# Senda PARRALAX program instruction construction (treasury layout v2)

`chain-client.mjs` constructs **real Solana transaction instructions** using Senda's existing `@solana/web3.js`. It targets the **v2** PARRALAX agent treasury (ItsNotAILABS/PARRALAX-AIHFTFUND PR #17, program source in `solana/programs/agent-treasury`). The IDL generated by `anchor build` for that source is vendored at `idl/parralax_agent_treasury.v2.json`, and `chain-client.test.mjs` checks every instruction's discriminator, account order, signer/writable flags and PDA seeds against it.

## Layout v2 (breaking vs. v1)

- Treasury PDA seeds: `["treasury", owner, mint, seed_id as u64 little-endian]`. Agent and beneficiary are **not** seeds any more, so the owner can rotate the agent without moving funds and run several treasuries per (owner, mint) with different `seed_id`s. The vault is the SPL associated token account of the treasury PDA for `mint`.
- `initialize(seed_id: u64, params: PolicyParams { per_tx_cap, daily_cap, lifetime_cap, expires_at }, guardian: Option<Pubkey>)`. Requires `0 < per_tx <= daily <= lifetime`, a future expiry, `agent != owner`, `agent != beneficiary`, `guardian != agent`. Freezable mints are refused unless allow-listed in the program (USDC mainnet/devnet are).
- Instructions and signers:
  - owner: `initialize`, `deposit`, `withdraw`, `update_policy`, `rotate_agent` (also clears `revoked`), `set_guardian`, `unpause`, `close` (drains the vault to the owner, closes vault + treasury, returns rent)
  - owner **or guardian**: `pause`, `revoke`
  - agent: `spend(amount, nonce)`; `nonce` must equal the account's `next_nonce` (read it with `decodeTreasury`)
- Errors (`TREASURY_ERRORS`): 6000 InvalidAuthority … 6009 Overflow, **6010 Paused** (was ClockRegression), **6011 Unauthorized, 6012 MintNotAllowed, 6013 InvalidExpiry** (new).
- `decodeTreasury(data)` reads the v2 account and refuses any other layout version.

## Program ID is configuration

`createTreasuryClient({ programId, verifiedProgramId, network })` requires an explicit cluster and a program ID that matches an independently verified ID. `treasuryConfigFromEnv()` reads `SENDA_TREASURY_NETWORK`, `SENDA_TREASURY_PROGRAM_ID` and `SENDA_TREASURY_VERIFIED_PROGRAM_ID` and returns `null` unless all three are set. The ID declared in the v2 source (`LOCALNET_PROGRAM_ID`, `5HJCtw…v61p`) is a **localnet/test key** and is refused on devnet and mainnet-beta.

No new Senda custody or signing path is introduced. Return the unsigned instructions to the existing connected-wallet review path **only after**:
1. Verified program deployment (non-placeholder, executable on intended cluster, pinned multisig upgrade authority and verified build hash).
2. Simulation of exact transaction and full instruction/account review.
3. Correct token mint, decimals, ATA owner and source balance checks.
4. Human approval to initialize/fund; isolated signer with owner-authorized budget for program-capped agent spends.
5. Independent confirmation of signature, exact SPL movements, and PARRALAX durable receipt reconciliation.
6. Explicit devnet/mainnet segregation and known upgrade authority; no automatic production fallback.

**Status:** instruction builder for v2, tested against the v2 IDL; not hooked into the running Senda UI. The program is built and tested on localnet only (anchor test) and is not deployed to any public cluster. Do not label this a completed mainnet/agent action loop.
